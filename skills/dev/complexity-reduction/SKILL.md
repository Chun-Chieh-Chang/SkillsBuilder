# Complexity Reduction (複雜度削減執行者)

簡單性不是做得少，而是**恰好做到需要的程度，不多也不少**。

複雜度是技術債的根源。過度設計浪費時間，且讓未來的修改更困難。

<HARD-GATE>
在 GREEN 步驟 (TDD)，不得：
- 添加超過讓測試通過所需的功能
- 重構「順手」看到的其他代碼
- 為「未來可能的需求」預先設計介面

只寫讓當前測試通過的最少量代碼。
</HARD-GATE>

## 三大原則

### YAGNI — You Aren't Gonna Need It
**不要構建你目前不需要的東西。**

觸發點：
- 「也許以後會用到...」
- 「如果需要擴展的話...」
- 「通用化一下比較好...」

以上想法出現時，刪除對應功能。等到真正需要時再加。

### DRY — Don't Repeat Yourself
**每一個知識點在系統中只應有一個唯一的、權威的表示。**

注意：
- DRY 是關於**知識的重複**，不是代碼的重複。
- 相似的代碼不一定是 DRY 違反。相同的**決策邏輯**重複才是。
- 過早抽象比重複代碼危害更大。

### 垂直切片 — Bite-Sized Tasks
**每次只做一件事，每件事 2-5 分鐘可完成。**

正確拆分示範：
- ✅ 「撰寫失敗測試」— 一個步驟
- ✅ 「執行確認失敗」— 一個步驟
- ✅ 「撰寫最小實作」— 一個步驟
- ✅ 「執行確認通過」— 一個步驟
- ✅ 「Commit」— 一個步驟

錯誤拆分示範：
- ❌ 「實作整個用戶認證模組」
- ❌ 「完成前端所有頁面」

## 複雜度偵測清單 (Self-Review)

在完成任何設計或實作後，對照以下問題：

**設計階段：**
- [ ] 我是否為「目前沒有需求」的功能設計了介面？→ 刪除
- [ ] 設計中是否有多個選項做同一件事？→ 選最簡單的
- [ ] 是否可以用 5 行代碼解決而我卻設計了一個模組？→ 直接寫 5 行

**實作階段：**
- [ ] 我加的代碼是否超過讓測試通過所需？→ 移除多餘部分
- [ ] 是否在 GREEN 步驟順手重構了其他東西？→ 還原，REFACTOR 再做
- [ ] 是否引入了新的依賴？→ 確認該依賴真的必要

**提交前：**
- [ ] 這個 commit 是否包含多個獨立的改動？→ 拆分 commit
- [ ] 文件/設計中是否有 TBD 或 TODO？→ 刪除或完成，不允許佔位符

## 過度設計的常見形式

| 模式 | 症狀 | 正確做法 |
|------|------|---------|
| 過早抽象 | 「先建一個抽象基類...」 | 直接實作，等第三次重複再抽象 |
| 配置驅動 | 「讓這個部分可配置，以後彈性...」 | 先寫死，等真正需要配置時再提取 |
| 框架思維 | 「這部分應該做成可插拔的...」 | 做最直接的實作 |
| 防禦性預留 | 「以後可能會支援多語系，所以...」 | YAGNI。等有需求再加。 |
| 大爆炸重構 | 「趁機把整個模組重構一下...」 | 只改需要改的，不影響本次需求的代碼不動 |

## 與其他 Skills 的整合

- **tdd-enforcer**：GREEN 步驟嚴格遵守此 skill 的最小實作原則
- **grill-requirements**：設計階段主動使用 YAGNI 剪枝，移除所有不必要功能
- **writing-plans**：計畫中每個任務粒度必須符合垂直切片（2-5 分鐘）
- **verification-before-completion**：完成前以此 skill 的清單做最終複雜度審查

## 🔗 Addy Osmani 精華整合 (from code-simplification)

### Chesterton's Fence 法則
在修改或移除任何代碼前，先理解它為何存在。如果你在路上看到一道籬笆卻不知道為何設置，不要拆掉它。先理解原因，再決定是否仍適用。

### 五大簡化原則
1. **保留行為不變** — 不改代碼的功能，只改表達方式
2. **遵循專案慣例** — 簡化意味著更符合現有代碼庫，而非強加外部偏好
3. **清晰勝於簡潔** — 明確代碼 > 緊湊但需要暫停思考的代碼
4. **保持平衡** — 警惕過度內聯、合併無關邏輯、移除必要抽象
5. **範圍限定** — 默認只簡化最近修改的代碼，不做無關的「順手重構」

### 簡化信號偵測表

| 類別 | 信號 | 簡化方式 |
|------|------|----------|
| 深層嵌套 (3+) | 控制流難以追蹤 | 提取 Guard Clause 或 Helper |
| 長函式 (50+行) | 多重責任 | 拆分為聚焦函式 |
| 巢狀三元 | 需要心理堆疊解析 | 改用 if/else 或查找表 |
| Boolean 參數旗標 | `doThing(true, false)` | 用 Options Object 或分離函式 |
| 通用命名 | `data`, `result`, `temp` | 改為描述內容的名稱 |
| 死碼 | 不可達分支、未用變數 | 確認後移除 |
| 過度工程模式 | Factory-for-a-Factory | 用最直接的方式替代 |

### 500 行規則
若重構需觸及超過 500 行，投資自動化（codemods、sed、AST 轉換），而非手動逐行修改。
